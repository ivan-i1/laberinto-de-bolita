1. What it does and does not do Current · Proposed

Phone tilt → Laberinto de Bolita → a ball rolling through a maze, reset when it falls. Proposed

Today: an Expo app (Android, iOS, web) that launches, shows the Base App demos and reads the tilt sensor. Current

It does not rotate the board in a physics engine, host anything, or reuse the private hyper-casual-game code or history.

Does

First deliverable, per the dump: navigating the plane. The tilt steers the ball; the ball stays centred and the maze moves (if the camera question settles that way; see §4).

Does not

Simulate a rotating 3D board. Tilt redirects gravity on a fixed plane; any visible board tilt is cosmetic. It has no backend, accounts, ads or leaderboards.

Public handoff

The JS bundle and assets, which will include every maze level. The repo itself is public.

Private machinery

This app's own upload keystore in credentials/ (gitignored, not created yet) and .env.local. Settings stay on the device.

A. One frame today: tilt rolls the ball into a screen edge Current

Setup: /demos/game-loop, 120 Hz phone, ball radius 22 (game-loop.tsx:50), 23 px from the left edge moving left at 3 px/frame.

Every block in this trace is a semantic display excerpt: return values of the real functions, not a stored or wire shape.

  1. A1expo-sensors → tiltSensor.ts:onSample

    A sample arrives every 16 ms. deviceToScreen negates X only (tilt.ts:38), then the calibration offset is subtracted and the result smoothed and dead-zoned into tilt.gravity.

    sample {x: 0.2, y: 0.1} g
→ screen {x: -0.2, y: 0.1}
→ tilt.gravity {x: -0.0432, y: 0.0216}
  2. A2game-loop.tsx:62 → bounce.ts stepBall

    Gravity is scaled by TILT_ACCEL 1.3 and dtf 0.5 (8.33 ms frame), integrated with friction 0.995, then the edge clamp reflects the ball at 70%.

    ball in  {x: 23, vx: -3}
ball out {x: 22, vx: 2.1143}
impact   3.0205
  3. A3SoundBank.ts, haptics.ts

    Impact over 1.5 plays a bounce sound and a light buzz unless the settings turn them off. This is the hook for "haptics on hitting a wall" (dump question 9).

  4. A4— maze branches here — Proposed

    In the maze, A2's edge clamp is replaced by collision against tiles in world coordinates, and the renderer draws the maze offset by screen centre − ball so the ball stays centred. Neither exists.

B. Ambiguous input: how the player holds the phone Verify

Nobody plays a maze with the phone flat. The same tilt sample means "steer" or "this is how I hold it" depending on calibration, and the dead zone decides when small tilts count.

  1. B1tiltSensor.ts:42–43

    Phone held 30° toward the player, otherwise level: the sample reads y = sin 30° = 0.5. Without calibration that is a strong downhill pull; calibrateTilt() (tiltSensor.ts:70) stores the current reading as the offset, so the same grip becomes level.

    Semantic display excerpt — tilt.gravity.y after 1, 3 and 10 samples

    SamplesNo calibrationAfter calibrateTilt()
    10.14500
    30.30050
    100.40870
    Result0.53 px/frame² downhillball rests

    Only the media demo has a Calibrate button (media.tsx:91). The game-loop demo never calibrates, so in the maze a calibration step is still to design.

  2. B2tiltSensor.ts:43 Verify defect

    The intended dead zone is 0.03 g (about 1.7°), rescaled so input starts from zero at its edge. But line 43 stores the dead-zoned value back into tilt.gravity, which is also the smoother's previous value. Starting from rest, one sample moves only 35% of the way, so anything under 0.03 / 0.35 ≈ 0.086 g is zeroed every sample and never accumulates.

    Semantic display excerpt — steady tilt.gravity.y for a held tilt past level, replaying line 43

    Held tiltSample (g)Output (g)
    2°0.03490
    4°0.06980
    4.9°0.08540
    6°0.10450.0188
    8°0.13920.0535
    10°0.17360.0879
    20°0.34200.2563

    So the ball ignores tilts under about 4.9°, and at 10° gets 0.0879 g instead of the intended 0.1436 g (about 60%). For a maze, where fine control matters, this is the first thing to fix: smooth first, store the smoothed value, and apply the dead zone only on output. The same code is in Base App (src/engines/sensors/tiltSensor.ts:43); __tests__/tilt.test.ts tests the two functions separately, not their feedback.

C. Boundary case: a fast ball meets an interior wall Proposed

No wall code exists. This is the failure the collider has to be designed against, from the dump's analysis (V1 §3.4) redone with this repo's numbers.

  1. C1bounce.ts stepBall Current

    The template has no speed cap: speed rises until friction balances the pull. Running the real stepBall in an open corridor:

    Semantic display excerpt — distance moved per frame once speed settles

    Held tilt (output)60 Hz120 Hz
    10° (0.0879 g)22.7 px11.4 px
    20° (0.2563 g)32.1 px32.0 px
  2. C2maze collider Proposed

    With nearest-point push-out, a step that carries the ball's centre past a wall's midline pushes it out the far side. That happens when one step exceeds radius + wall/2. For radius 22 and an illustrative 20 px wall, that is 32 px, which a 20° run reaches after about 2 s at 60 Hz.

    Threshold 22 + 20/2 = 32 px; settled step at 20° ≈ 32 px. That is marginal, and a steeper tilt passes through.

    So the collider needs sub-steps no larger than min(radius, wall/2) per frame, or a speed cap below the threshold. The dump flags this as the natural first red→green test. Wall thickness and ball size are open (Q5).

4. Decisions: settled and open Proposed

The design lives in two dump files, ADV-REV-laberinto-V0.md (the idea) and ADV-REV-laberinto-V1.md (a fact-check of it, 2026-09-28). Neither is committed: they sit untracked in the root of the primary checkout, so they are named here, not linked.

Settled

  • Current Gravity redirect on a fixed plane, not a rotating board. No 3D physics engine is usable on React Native 0.81 (V1 C2), and the template already steers this way (A2).
  • Current Start clean from the public Base App, no private history. V1 warned that the public repo must not inherit the private hyper-casual-game history (U2) and that the Gradle .gitignore was wrong (U1). PR #1 does both: copied from Base App, Expo .gitignore. Repo visibility (public) was not explicitly re-confirmed.
